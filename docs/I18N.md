# Internationalization (i18n)

Document Scanner ships two UI languages: English (`en-US`) and Simplified
Chinese (`zh-CN`). Language handling lives entirely in `scanner-app`;
`scanner-core` and `scanner-cli` remain language-independent.

## Design

- Locale catalogs are the YAML files under `assets/locales/`. They are
  embedded into the binary at build time with `include_str!` and flattened
  into dotted keys (`toolbar.open_files`). There is no runtime file lookup.
- `crates/scanner-app/src/i18n.rs` owns the `I18n` message catalog, the
  `LanguagePreference` setting (`Auto` / `English` / `Chinese`), and system
  locale detection through `sys-locale` with an `LC_ALL`/`LANG` environment
  fallback.
- `I18n::tr(key)` returns an owned `String` and falls back to the raw key
  when a message is missing, so an untranslated string is visible in the UI
  instead of blank. `I18n::text(key, values)` substitutes `{name}`
  placeholders for interpolated messages.
- UI modules (`ui/toolbar.rs`, `ui/queue.rs`, `ui/inspector.rs`,
  `canvas/mod.rs`) receive `&I18n` (or hold it on `ScannerApp`) and never
  hardcode user-facing prose. Enhancement preset names are translated via
  `I18n::preset_label`; output format names (`JPEG`, `PNG`, `BMP`, `TIFF`)
  stay as-is because they are proper nouns.
- The toolbar contains a **Language** picker with three options: follow the
  system default, English, and 简体中文. Changing it rebuilds the catalog
  immediately and also updates the native window title.
- The selection persists to `preferences.json` inside the platform
  configuration directory (resolved via the `dirs` crate; see
  `crates/scanner-app/src/preferences.rs`). A missing or malformed file
  falls back to `Auto`. A failed write is logged with the `[preferences]`
  prefix and shown in the status bar.
- Chinese glyphs render correctly because Source Han Sans SC is bundled and
  set as the primary UI font (see commit `24c7bb1`).

## Known scope limits

- Error strings produced by `scanner-core` workers (decode failures,
  geometry rejections, export I/O) are shown verbatim and are currently
  English-only. Translating them requires structured error codes in core and
  is not implemented.
- Status-bar messages pushed before a language switch keep the language they
  were created in; only new messages use the new language.
- The CLI output is English-only (automation surface, not localized).

## Adding or changing strings

1. Add the key to `assets/locales/en-US.yaml`.
2. Add the same key with a translation to `assets/locales/zh-CN.yaml`.
3. Reference it via `i18n.tr("your.key")` in UI code.

`i18n::tests::locale_resources_have_the_same_keys` fails if the two catalogs
diverge, and `locale_values_are_never_empty` fails on blank translations.

## Debugging

Language switching logs with the `[i18n]` and `[preferences]` prefixes:

```bash
cargo run -p scanner-app
rg "\[(i18n|preferences)\]" debug.log > focused-debug.log
```
